## New breakage in the fix diff

### Important N1: selected cached prefetch can stall behind evictable visible-lane cache

**Priority P1.** `packages/zyren_3d_tiles/lib/src/streamer.dart:209` checks whether promotion fits but never makes room by evicting unselected, unpinned visible-lane entries. `:723` then skips the selected tile because it is already cached, before the ordinary admission eviction loop at `:756`. Coverage at `:980` excludes unpromoted speculative content. This can leave an available selected tile permanently outside the candidate cover, despite sufficient capacity after an allowed eviction.

Minimal state and route:

1. Configure one-tile speculative quotas and two-tile visible quotas in both dimensions. Use a reusable non-provider resolver, such as the existing `MemoryResolver` fixture, with three equal-sized tile payloads. Set per-tile decoded/resident reservations to their measured payload sizes and total caps to three times those sizes.
2. Display tile A, then move to D and accept D. A remains fresh in the cache but is now unselected, unpinned and eligible for ordinary admission eviction. A and D together consume the two-tile visible quota. A is no longer in the adjacent/predicted prefetch selection.
3. Let neighboring B finish prefetch in the one-tile speculative quota. Move the camera so B is selected. No other uncached visible request is needed or active.
4. Promotion sees A+D+B exceeding the visible quota and refuses B, even though evicting A would leave the valid D+B overlap. `_pump` skips cached B, so it never reaches the eviction loop that would remove A for an equivalent uncached visible request. The old displayed D persists under tracked publication; synchronous untracked use can instead leave no visible replacement.

This is not the explicitly approved wait behind pinned cover. Only D is pinned in this trigger; A is available to reclaim. It is also not a physical cancellation delay: all loads can already be drained.

Ordinary updates do not guarantee recovery. `_discardInactive` at `:1219` intentionally retains fresh non-provider cache, so it does not remove A. A stationary update at `:397` can return without another refresh, while repeated `completeFrame` calls or full refreshes merely repeat the failed promotion. Speculative-only request pumping can evict only its own lane. With no additional uncached visible request, freshness expiry, explicit reset or other view change that happens to force eviction, this state makes no progress.

Fix direction: admit cached promotion through the same visible-lane room-making policy as new visible requests, reclaiming only unselected and unpinned entries and checking both byte dimensions. Preserve the displayed/staged/submitted cover and physical request reservations. Promotion must become eligible again when publication retirement creates room. Do not bypass the partition or evict pinned cover.

Missing regression: use the A -> D -> prefetched B sequence above with tracked receipts. Assert A is retained but unpinned before selecting B, B is not fetched again, A is reclaimed, B becomes candidate/displayed within the existing finite bound, and counters stay within both quotas throughout. Repeat update/completeFrame with no unrelated loads. Keep the current pinned-cover test unchanged as the rejection control. The new sequential-request tests exercise uncached D/E admission, which already reaches the eviction loop; the new promotion test intentionally pins the full visible quota, so neither covers this reclaimable-cache case.

This finding follows directly from the changed control flow and current freshness/eviction semantics. No new runtime reproduction or suite run was performed during this read-only review.

- The deferred-copy transaction solves the original in-place corruption rather than merely restoring map entries.
