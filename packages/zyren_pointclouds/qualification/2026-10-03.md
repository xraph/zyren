# Reality capture qualification, 2026-10-03

The point and Gaussian packages now have native source import, spatial streaming,
perspective scene rendering, shared domain adapters and live MCP evidence. You can
reproduce the checks with Flutter 3.47.5. iPhone and iPad qualification still need a
device run. The app's own ID is blocked by signing quota; a temporary iPhone build
signed with an existing profile reaches the separate installed-app limit.

The Flutter lab imports the encoded fixtures and checks their original attributes.
Its visible point and Gaussian grids are generated source data for LOD and rendering
checks, not a reconstruction of those survey fixtures.

Both native presentation runs reported 16 visible point chunks, 16 Gaussian chunks,
36 projected Gaussians, no active requests or reserved payloads after settling,
and zero readback bytes. The pixel assertions are separate offscreen captures and
intentionally read pixels. Final closure drained both decoded streams to zero.

Machine-readable summaries are [macOS](macos-metal.json), [Pixel](pixel-vulkan.json)
and [live MCP](live-mcp.json). [Fixture hashes](fixture-sha256.json) match the app's
asset copies against the package's source fixtures. Raw local JSON-RPC output lives
under ignored `artifacts/reality-capture/live-mcp.json`.

The native desktop window was inspected directly: all fixtures loaded, the scene
was visible, controls changed labels, and section clipping removed the negative-X
points while retaining the Gaussian scene and its opaque occluder. Narrow phone
layout wraps the controls. A fixed camera initially cropped the scene on Pixel;
the app now fits its width to the current viewport, and the final integration run
selected all 16 point chunks. Text and native viewport semantics are present.

## Reproduction

Run package tests from each package directory so the Dart native build hook owns
its assets. Use `fvm dart`, since the default shell Dart is older than this workspace.

```sh
RUN_NATIVE_GPU=1 fvm dart test --concurrency=1
```

From `packages/zyren_pointclouds/example/qualification`:

```sh
fvm flutter test integration_test/capture_test.dart --no-pub -d macos
fvm flutter test integration_test/capture_test.dart --no-pub -d <pixel-device-id>
fvm flutter drive --no-pub --publish-port \
  --driver=test_driver/integration_test.dart \
  --target=integration_test/capture_test.dart -d <wireless-ios-device-id>
python3 tool/verify_mcp.py 'fvm dart run tool/live_mcp.dart' /tmp/reality-mcp.json
fvm flutter build ios --debug --no-pub --no-codesign
```

The device suite waits for native scene work, not just a Flutter pump duration.
An early run failed because loading completed before the next scene frame; a
second timing check now waits for filter application. Assets initially referenced
files outside the app and were not bundled correctly. All four fixture copies now
live in the app's `assets` directory. The successful runs used those fixes.

## Limits and blockers

Apple reports: “Your maximum App ID limit has been reached.” The account allows
ten new IDs per seven days, and Xcode has no development profile for
`dev.zyren.realityCapture`. Retrying after the phone was unlocked produced the same
signing error. The iPad attempt also reached Xcode signing and failed with both
errors. The unsigned `Runner.app` builds but cannot be installed as device
qualification. A suitable development team/profile or reset of the account limit
is required for this bundle ID. These initial attempts did not reuse another
app's bundle identity.

The discovered iPad ran iPadOS 27.0 (24A437) and connected over Wi-Fi. The first
`flutter test` attempt stopped before building because wireless iOS requires VM
service port publication, but `test` does not accept `--publish-port`. Retrying
through `flutter drive --publish-port` reached signing and produced the account
quota error. Its host driver was a temporary copy of the checked-in three-line
driver. Local logs are `/tmp/reality-ipad-qualification.log`,
`/tmp/reality-ipad-published-port.log` and `/tmp/reality-ipad-drive.log`.
The retry was stopped after it tried to launch the cached unsigned app. No iPad
rendering, import or cleanup pass is claimed.

The later iPhone retry built the integration target again without signing, then
copied the generated app to `/tmp/reality-apple-qualification`. The temporary
copy uses the existing `dev.gpu3d.multipleViews` identity and its unexpired profile,
which includes the iPhone 16 Pro. The app's embedded profile, bundle ID and signing
entitlements match; all nested native code and the app were signed with the
profile's development certificate. `codesign --verify --deep --strict` passed.
The project still uses `dev.zyren.realityCapture`.

Installation reached a different error: the iPhone already has three apps using
free development profiles, Planet, Scientific Lab and Zyren Xr Probe. The installer
reported `MIInstallerErrorDomain` code 13 and listed those three identities.
The local log is `/tmp/reality-iphone-existing-id-install.log`. This is a separate
limit from registering new IDs. Apple documents both in its
[developer account overview](https://developer.apple.com/help/account/basics/about-your-developer-account).

A second temporary copy is signed for the XR demo's existing identity. A signed
XR restoration build is saved beside it. Replacing that installed demo is awaiting
the user's approval; no app was removed or replaced by this retry, and no iPhone
tests have run. The signing profiles and signed app copies remain outside Git.

The verified MCP launch is `dart run`. A standalone AOT executable compiled but
could not create the native backend. It is not qualified. No MCP network endpoint
or independent agent protocol was introduced.

Gaussian sorting is on the CPU, by mean depth. Intersecting volumes and ordering
against transparent scene meshes remain approximate. Higher-order spherical
harmonics, PLY and GPU sorting remain future work. Source metadata does not prove
survey accuracy, CRS conversion or tile membership. The geospatial tests use
synthetic local fixtures, not a live external survey or tiles provider.

Payload counters do not measure total process memory or physical GPU residency.
Offline hierarchy builders retain their source copies; large datasets need a
storage-backed loader. The scene renderer preallocates its configured GPU capacity,
while stream GPU counters describe the visible cut. Large-dataset performance and
forced physical device-loss recovery are unverified.

Checks ran in a shared checkout with concurrent core and plugin work. These results
qualify the owned source and exercised paths, not a clean release of unrelated
changes. No package was published, pushed or merged.
